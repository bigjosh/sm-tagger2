# sm-sorter / sm-tagger — Implementation Guide

This document defines **how** version 1 is implemented. [`spec.md`](spec.md) defines **what** the programs must do and **why** those behaviors exist. If this document ever conflicts with the behavioral specification, the specification wins and this document must be corrected.

[`storage-reference.md`](storage-reference.md) defines the canonical directory trees, filenames, and persisted byte formats. Use its [runtime trees](storage-reference.md#runtime-directory-trees), [creation responsibilities](storage-reference.md#required-directories-and-creation), and [message-state suffixes](storage-reference.md#message-state-suffixes) when implementing the operations below. Concrete paths and suffixes here identify algorithm steps; they do not establish separate storage definitions.

The implementation should be changed when a simpler design preserves the specification's observable behavior. Exact library calls, class names, and project boundaries in this document are engineering choices rather than public compatibility promises.

## 1. Language and code-quality rules

- Implement both programs in **pure managed C#**. Do not use C++, handwritten P/Invoke, `unsafe` code, a native helper DLL, or direct Win32 calls.
- Target Windows on `net10.0` (.NET 10 LTS). Pin the approved SDK feature band in `global.json` and keep the installed runtime/SDK on a supported servicing patch. Use the .NET base class library unless a dependency provides clear value that cannot be obtained simply from the platform.
- Produce two console applications: `sm-sorter.exe` and `sm-tagger.exe`.
- Favor simple, direct, readable code over framework-building, clever abstractions, and speculative flexibility.
- Give a concept one representation and one implementation. In particular, share the physical-line scanner and address parsing/canonicalization primitives. The sorter alone uses the fast classifier; the tagger builds its full HDR interpretation directly from those shared primitives rather than scanning the HDR twice.
- Put a brief comment immediately before every function or method explaining its responsibility. Add comments anywhere else a future reader would benefit from understanding **what** a non-obvious block establishes or **why** the design requires it. Do not add comments that merely translate obvious syntax into English.
- Use descriptive domain names such as `privateAddress`, `recipientId`, `parentBasename`, and `publicationState`. Avoid unexplained abbreviations.
- Keep functions focused. Prefer explicit control flow and small domain types over deeply nested callbacks or generic machinery.
- Do not catch an exception at a point that cannot recover, add necessary state context, or deliberately convert it to a specified message/startup failure. Let unexpected exceptions reach the nearest meaningful message or process boundary and ultimately the console.

The build enables nullable reference types, deterministic builds, analyzers, and warnings as errors. Formatting is enforced by the normal .NET tooling rather than by hand-maintained style rules.

Target the latest generally available production SmarterMail and Windows Server releases at bring-up and record their exact tested builds in `assumptions.md`. Keep the registry's `VERSION-SENSITIVE-*` identifiers in comments immediately beside code that depends on those external behaviors. Those markers identify upgrade regression checks, not runtime version detection or compatibility branching.

## 2. Trust and validation policy

Validation belongs at trust boundaries, not after every assignment.

### 2.1 Trusted conditions

Version 1 deliberately trusts the following deployment conditions:

- The sorter singleton and both tagger singleton locks are successfully enforced before either program performs its protected work.
- Each program processes only one message at a time.
- The configured datadir, spooldir, their permissions, and their filesystem topology were installed correctly and remain under trusted administrative control.
- Every source/destination pair used for a mail transition is on the spool's ordinary local NTFS volume. The fixed Proc mailroot has no junction/reparse redirection and is inert to SmarterMail under the accepted owner-confirmed assumption. Configuration/mappings may use a different NTFS volume, with mapping staging and publication together there. Placement and permissions remain trusted installation conditions, without new runtime preflight.
- Administrators do not edit the datadir, replace files, change topology, or write to program logs while the owning tagger is running, except through the documented stopped-tagger update procedure.
- SmarterMail-generated basenames are unique for the required retention window.
- Operator-provisioned templates never generate overlong addresses (`ASSUMPTION-TEMPLATE-LENGTH` in `assumptions.md`); do not add a runtime transport-address-length gate.
- Values generated by this software or deliberately provisioned by the trusted administrator—UUIDs, sender-ids, configured auth/private addresses, and generated tag addresses—are not adversarial strings.

Code should not add locks, retries, existence probes, post-operation verification, repeated parsing, or path-hardening layers solely to defend against a violation of those conditions. If a trusted condition later becomes false, change the trust model and design explicitly rather than accumulating scattered defensive checks.

### 2.2 Inputs that still require validation

The following remain real boundaries:

- HDR and EML bytes may be malformed, unsupported, incomplete, or inconsistent with the approved SmarterMail/client behavior.
- Configuration and persistent identity records may be missing, partially written, stale, or accidentally malformed when loaded at startup. Existing diagnostic log contents are accepted without validation under §4.6.
- Filesystem operations, allocation, encoding, and random-number generation can fail.
- An existing destination name can collide with a proposed message child or tag address.
- Arithmetic based on file lengths or recipient fan-out must not overflow the selected .NET representation.

Validate each value once when it crosses its boundary. Thereafter, represent the validated state with a type or object that makes revalidation unnecessary. Program-generated transformations should be covered by unit tests; they do not need a second defensive parse in production unless the specification requires a genuinely new boundary check.

## 3. Solution structure

Keep the dependency direction obvious:

1. A small shared layer referenced by both programs contains the byte-level physical-line scanner, bare addr-spec parsing/canonicalization, filename-component rules, and the sorter fast classifier.
2. Sorter code contains only sorter decisions and its small queue state machine. It must not reference or carry the full HDR/EML mailbox parser, recipient-id codec, edit planner, sender-id record loader, tag store, or tagger processor.
3. Tagger-only mail code contains full HDR interpretation, logical EML fields, bounded mailbox and Content-Type parsing, recipient-id encoding, and byte-edit planning/application.
4. Tagger application code contains sender-id record loading, mapping persistence, transformation, fan-out, publication, and tagger logging.
5. Each executable has a thin composition root for arguments, singleton acquisition, watch/one-shot selection, console shutdown, and top-level exit handling.
6. Tests reference the same production code. Test-only fakes and fixtures must not be reachable through production command-line options, environment variables, configuration files, or message data.

These may be separate projects or clearly separated namespaces in a small number of projects. Do not create an interface for every class merely to satisfy this outline.

## 4. Managed platform operations

### 4.1 Singleton

**VERSION-SENSITIVE-004:** Verify the actual Windows/.NET sharing and singleton behavior on the installed platform and after relevant updates.

Open each persistent lock file with `FileMode.OpenOrCreate`, read/write access, and `FileShare.None`, and retain its `FileStream` for the lifetime of the invocation. This provides the required cross-process singleton. Lock filenames remain on disk after exit; ownership is the open handle, not file existence. Use the locations defined in the [lock reference](storage-reference.md#locks).

The sorter acquires its Proc lock before queue work or its requested email log. The tagger acquires the data lock first, calls `Directory.CreateDirectory` for the fixed mailroot, and acquires its queue lock next; only then may it open the optional datadir trace, load configuration, or touch queue messages. Keep both tagger streams alive for the entire invocation and dispose already-acquired streams on any later startup failure. The queue lock rejects two datadirs consuming one spool; the data lock rejects one mapping set used by two spool taggers. Do not wait/retry contention or add a named mutex or in-process lock.

### 4.2 Files and directories

**VERSION-SENSITIVE-001, VERSION-SENSITIVE-003, VERSION-SENSITIVE-004:** Queue visibility, derived basename uniqueness, and local NTFS move semantics require verification on the installed deployment.

- Centralize the [literal-component rules](storage-reference.md#identifiers-and-addresses), using `Path.GetInvalidFileNameChars()` alongside the explicit Windows name checks. Apply the same predicate to a canonical message auth-address before constructing its routing-index path; failure there produces the specification's structurally-unenrollable direct-pass result rather than a lookup. Validate once, then combine with the trusted root. Derive child names from the validated basename using the [message naming contract](storage-reference.md#message-state-suffixes).
- Use `File.Move(source, destination, overwrite: false)` for queue state transitions and file publication.
- Use `Directory.Move(source, destination)` to publish a complete staging mapping directory.
- Rely on the supported-deployment requirement that every such move is within one NTFS volume. Do not add a volume, mount-point, reparse-point, ACL, destination-existence, or filesystem-type preflight.
- `File.Move` may implement a cross-volume request as copy-then-delete. That behavior is non-atomic and therefore outside the supported deployment; without a volume preflight, a misconfigured installation is not guaranteed to fail fast. This is why the real configured paths must pass the same-volume installation test before use and after topology changes.
- Use `FileMode.CreateNew` for child files and diagnostics that must never replace an existing artifact.
- Use `File.Copy(source, destination, overwrite: false)` for `-keep` evidence.
- Use `File.Delete` for successful parent cleanup. Cleanup is defined by the postcondition that the parent is absent; an already absent file is success.
- Use `Directory.CreateDirectory` for required parent directories. Its idempotent existing-directory behavior is acceptable in the trusted administrative tree.

For a new mapping, generate a fresh UUID staging name. Because the tagger singleton is held and the staging namespace is trusted, require that one proposed name to be absent and then use `Directory.CreateDirectory`; an unexpectedly existing UUID is a message failure, not a reason to add retry machinery. Create and close both required identity files with `FileMode.CreateNew`. Separately attempt to create and close an empty `tag-log.txt`; catch and report a failure through the best-effort logging path and continue. Only identity-file completeness is required before `Directory.Move` publishes the mapping. An existing final tag directory is the normal tag-token collision result.

Do not probe a destination immediately before moving to it. The move itself determines whether the destination was available. Never delete or replace a colliding live destination and never emulate a failed queue move with copy-and-delete.

### 4.3 Complete writes and closing

Encode complete file contents before opening the destination when practical. Write through a `FileStream`, then dispose it before making the file ready or publishing its containing directory. A thrown write, flush, or dispose exception means the file did not complete successfully.

.NET deliberately abstracts native short-write loops and handle closing. Judge success by the managed operation completing without exception; do not attempt to expose native `WriteFile` byte counts or `CloseHandle` return values.

Stable-media persistence through machine or power loss is outside version 1. Do not use write-through flags or force physical-media flushes. Do ensure no application-managed buffer remains unwritten before a state transition that advertises a completed file.

### 4.4 Randomness, UUIDs, and time

- Use `RandomNumberGenerator.Fill` for tag-token bytes. There is no weaker fallback.
- Use `Guid.NewGuid()` for run and staging identifiers and format them as canonical lowercase `D` strings.
- Use `DateTimeOffset.UtcNow` through a small clock dependency wherever deterministic timestamp tests need control.

Inject the clock and tag-byte source into the tagger behavior that consumes them. A UUID source may also be injected where deterministic collision tests benefit. Do not generalize this into a service locator or runtime-selectable provider.

### 4.5 Watching and orderly shutdown

**VERSION-SENSITIVE-013:** Watcher recovery, rescan behavior, console events, and the chosen process host require upgrade regression checks.

Use `FileSystemWatcher` only as a wake-up hint:

- watch the direct input directory, not subdirectories;
- enable filename notifications before the first complete scan so startup arrivals and final-file renames can wake the loop;
- ignore event names, event kinds, ordering, and cardinality;
- after a wake-up, enumerate the direct directory and filter regular files by the role's exact final extension using `StringComparison.OrdinalIgnoreCase`: `.eml` for the sorter, `.hdr` for the tagger; do not depend on wildcard matching semantics;
- perform the same scan after 30 seconds without a useful notification;
- materialize and sort every scan's basenames with `StringComparer.Ordinal`, then process them sequentially;
- recover an overflow by scanning; treat an unrecoverable watcher error as fatal to that executable.

Use a small thread-safe signal to wake the otherwise sequential processing loop. Event callbacks must not process mail themselves.

Use `Console.CancelKeyPress` for Ctrl+C/Ctrl+Break. Set `e.Cancel = true`, record the stop request, and wake the loop. Check the stop request before claiming each message. Finish an already owned message, then dispose the watcher and every held singleton and return normally unless a specified fatal failure occurred during completion or shutdown. Do not build a more elaborate cancellation state machine solely to expose internal `FileSystemWatcher` cancellation steps.

One-shot mode constructs no watcher.

### 4.6 Log files

Implement the record formats and encodings in [logs and diagnostics](storage-reference.md#logs-and-diagnostics). Keep the sorter's small diagnostic writer in the sorter project; do not reference tagger `TraceLog`, configuration, mapping, or EML parsing code. With `-l`, open the operator-selected email log after acquiring the sorter singleton and retain its append stream for the invocation. Resolve relative paths from the working directory and flush each terminal record. Do not create parent directories or inspect existing log bytes. Formatting/open/append/flush/dispose failures report to stderr, disable that file for the invocation, and preserve current and subsequent mail processing. Never rotate, repair, reopen, or retry it during that invocation. With `-v`, emit the separate debug stream to stdout; a console failure disables only debugging and attempts a stderr report.

Only the singleton tagger writes its `log.txt` and tag logs. Other processes may read them but concurrent external writes while the tagger runs are unsupported. The sorter email log is a separate operator-selected file with the same no-concurrent-writers expectation.

When `-log` is requested, attempt to open `log.txt` once in append mode with write access and `FileShare.Read`. Encode each event into one application-level buffer and attempt to flush managed buffering before the related state mutation proceeds. If opening, encoding, writing, flushing, or disposing fails, report the operation and error to standard error and disable file tracing for the rest of the invocation. Dispose an acquired failed writer on a best-effort basis; its cleanup must not throw into the mail-processing boundary. Do not reopen or retry it in that invocation. Startup, current mail, later mail, and shutdown continue normally.

For a tag log, use append mode with write access and `FileShare.Read`, creating a missing file when possible. Encode, append, flush, and dispose the entry before attempting the child's EML move. Catch logging-operation exceptions, report them to standard error, and continue the remaining distinct tag logs in ordinal tag-address order and then the same child's publication. Do not retry a failed entry for that child; later children and messages attempt their own entries normally. Empty tag-log creation during mapping allocation uses the same nonblocking error policy.

For every file log, append without reading, decoding, or validating prior contents. Accept missing, corrupted, and unterminated logs. Do not repair or truncate them, insert recovery separators, or mark a mapping unusable because of logging. Do not inspect tag-log presence or accessibility at startup. Log formatting and I/O errors must not escape into mapping, message, or startup failure handling. Standard-error reporting is itself best effort, with no recursive fallback.

Do not promise one native write call or expose native close status. Each logging call reports its own managed operation failure without changing mail decisions or exit status. A publication-attempt entry is optional diagnostic evidence; a successful child may have no recorded entry.

## 5. Parsing and byte-preserving edits

Treat spool files as bytes, not as text documents to normalize and serialize.

### 5.1 HDR

**VERSION-SENSITIVE-002, VERSION-SENSITIVE-005, VERSION-SENSITIVE-006:** Trusted `auth:`, HDR framing, null paths, and `notify:` semantics depend on the approved SmarterMail routes and captured fixtures.

Build one physical-line scanner that recognizes CRLF boundaries and returns slices or offsets into the original byte array. The fast classifier and full parser share this scanner and implement the [HDR format and input grammar](storage-reference.md#input-grammar).

The fast classifier should inspect all metadata lines for `auth:` so duplicates are not missed. Validate the common `key:` shape of every metadata line, but do not parse unrelated values. It returns only `NoAuth`, `ValidAuth`, or `Unsafe`.

The full parser retains positional lines and ordered metadata occurrences. Do not convert repeated metadata into a dictionary. Parse only fields used by the behavior; preserve unknown lines as opaque bytes.

### 5.2 EML

**VERSION-SENSITIVE-005, VERSION-SENSITIVE-011, VERSION-SENSITIVE-012:** Client header grammar, opaque identity-bearing content, and MDN behavior require fixtures for each supported version/path.

Find the first CRLF/CRLF boundary and parse only the preceding header bytes. Represent each logical field as its complete original range plus any parsed addr-spec ranges. Preserve the body as the untouched suffix of the original byte array.

Recognize the optional EML preamble defined in [message files](storage-reference.md#message-files). Scan physical header lines after that prefix, but add its length back to each recorded line start. Keep the original source array and one-byte-per-character header view intact, so all field, value, and mailbox positions remain absolute offsets into the complete source. The first field starts after the prefix; it must not own the prefix bytes. Do not add this behavior to the shared HDR scanner, decode the message as UTF-8, strip any bytes, or retry parsing with progressively looser rules.

Removing an initial `Return-Path:` must leave the preamble at byte zero. Copying a From field to synthesize Reply-To begins at the field's range and must exclude the preamble. Ordinary byte edits preserve the prefix once without a special output rewrite. Preserve malformed-prefix failures under the existing retention rules; repeated/partial/other-encoding prefixes and later field-name prefixes receive no tolerance. SmarterMail build 9742's immediate API path motivated this exception; producer and consumer behavior remain `VERSION-SENSITIVE-005` checks described in [the compatibility follow-up](bom-compatibility-2026-09-16.md).

Implement the bounded [mailbox and Content-Type grammar](storage-reference.md#input-grammar) directly. Do not use regex replacement or `System.Net.Mail.MailAddress`, both of which obscure accepted syntax and original byte ranges.

### 5.3 Canonical addresses and edits

Implement [canonical address identity](storage-reference.md#identifiers-and-addresses) with explicit ASCII casing rather than culture-sensitive casing. Retain original recipient bytes separately for the child's HDR recipient line.

Build and decode recipient-ids using the [identifier codec](storage-reference.md#identifiers-and-addresses). On load, remove only its permitted terminal line endings, decode, and require re-encoding to reproduce the remaining bytes exactly. This round-trip check rejects noncanonical persistent records without a separate normalization path.

Construct edits from parser-owned, disjoint original ranges so ordering and non-overlap hold by construction, and cover that invariant in tests. Apply replacements/removals from the highest offset to the lowest. Insert a synthesized `Reply-To:` immediately after its source `From:` field. This preserves every byte outside explicit edits without adding a redundant production recheck.

Use the parsed physical-line boundaries and planned replacement bytes to check the resulting length of every changed physical EML header line, and every physical line of a synthesized `Reply-To:`, against the 998-byte limit excluding CRLF in `spec.md` §8.1. Include the synthesized field name, all retained bytes on the affected line, and continuation indentation. Check after the actual individual/group tags are known and before either child file becomes `.pend`. This check does not scan unchanged lines or bodies and does not refold output.

The parsed physical-line length excludes an optional preamble, so add its length when checking the first physical line of the first surviving original field. Find that field after excluding all Return-Path removals, including folded or repeated leading Return-Path fields. Do not charge the prefix to later fields, continuation lines, or synthesized Reply-To. Keep the current changed-line selection rule; an otherwise unchanged first line does not acquire a new length check merely because the file has a preamble.

Do not reparse a completed output merely to prove that the deterministic edit code did what its types and tests already establish.

## 6. In-memory models

Use small immutable records for validated values such as canonical addresses, sender-id records, recipients, logical fields, and child plans. Avoid inheritance hierarchies.

The existing internal `SenderProfile` type represents the [sender-id record](storage-reference.md#sender-configuration); its type name does not imply a directory name. Resolve configuration and staging locations from the [runtime directory contract](storage-reference.md#runtime-directory-trees).

Load one immutable sender/configuration snapshot at tagger startup. Use ordinal dictionaries/sets keyed by canonical strings for:

- every published auth-address → sender-id record, allowing many distinct auth keys for one record;
- sender-id → sender-id record.

Build the auth dictionary only from validated index directory names and their pointers; sender records contain no reverse auth list. Load and retain complete records with zero indexes so historical mappings remain valid. Preserve global uniqueness of private addresses and reject auth/private collisions. Every account sharing a record uses the same template, private-address, MDN policy, and `(sender-id, recipient-id)` mapping key.

Initialize a separate mutable `(sender-id, recipient-id)` → tag-address dictionary from the validated live records. Only the singleton tagger writes it, immediately after a new mapping directory is published. Treat this dictionary as the running mapping authority, not as part of the immutable configuration snapshot.

The singleton makes these ordinary in-process collections sufficient. Do not use concurrent collections, database transactions, lock-free algorithms, or cross-process mapping locks.

Precompute the complete child plan and all byte edits before publishing any child. Persistent mapping creation may occur while materializing those plans because the final tag address is required in the output bytes. A newly published mapping is permanent even if later child creation fails. An output-header-length contract error publishes no child, retains the `.break` parent and any inert child files in their actual states, and leaves published mappings available for reuse.

## 7. Sorter implementation

After acquiring the sorter singleton in watch mode, enumerate direct sorter-owned residuals such as `.hdr.sort` and `.sort.err` in `proc` and report them to standard error without opening, repairing, or removing them. Then begin the ordinary final-EML scan. Do not scan or watch `<mailroot>\failed`, or move older retained Proc files there. One-shot mode acts only on its requested plain basename and is not a residual-reporting or repair command.

Open the requested email log only after singleton acquisition. When verbose output is enabled, report startup/shutdown, queue scans, readiness deferrals, classification/routing, file-operation intents/results, stale entries, and terminal outcomes through stdout debugging. Keep these process/operation events out of the email log; its records follow the [sorter log format](storage-reference.md#logs-and-diagnostics).

For each selected final EML:

1. Call `File.GetAttributes` on the EML before any HDR read or probe. `FileNotFoundException` or `DirectoryNotFoundException` means `Stale` in watch mode or `Deferred` with `EML_NOT_AVAILABLE` in one-shot mode. A directory or another attribute failure means `Hold` with `INPUT_READINESS_FAILED`. Never open or read EML contents, and do not add a separate EML lock or content-completeness probe. This ordering keeps HDR-only attempts entirely outside processing.
2. Read the matching same-basename plain HDR with `File.ReadAllBytes`, using read-only access and `FileShare.Read` to exclude active writers. Its handle is closed when the call returns, before ownership. Preserve the existing missing-HDR distinction between watch and one-shot modes. An `IOException` identifying Windows sharing/lock violations defers before ownership with `HDR_BUSY`; another read failure becomes `Hold` under the existing retention path.
3. Locate the first CRLF and trim trailing ASCII SP/HTAB from its status bytes for comparison only. Compare case-sensitively: `Written` permits the existing shared fast HDR classifier and auth-index lookup; `Failed` means `Hold` with `UPSTREAM_FAILED` under the unchanged retention branch, without auth lookup; `Writing` returns `Deferred` with `HDR_WRITING`. Every other value, including `Quarantined`, `Ready`, wrong case, empty status, or missing first CRLF, returns `Deferred` with `HDR_STATUS_UNEXPECTED`. Report the unexpected status to stderr on every encounter in either mode regardless of flags; do not add deduplication state. Neither deferral reads EML contents or looks up auth. After a valid `Written` line, malformed remaining HDR framing is still `UNSAFE_HDR`.
4. Claim the HDR by moving it to `.hdr.sort`.
5. On `Pass`, move EML then HDR to the spool root. On `Divert`, move EML then HDR to `process`. For `UPSTREAM_FAILED` only, call `Directory.CreateDirectory` for `<mailroot>\failed`, move the plain EML there, then move the owned HDR there retaining `.hdr.sort`. Use non-replacing moves and update the tracked current path immediately after each successful move. Stop at the first failed operation; keep completed moves. Other holds leave the claimed pair in Proc. Only holds and failed handoffs attempt a diagnostic beside the current owned HDR; successful `Pass` or `Divert` creates no error diagnostic.
6. Attempt exactly one terminal email-log record: `PASS` or `DIVERT` only after the complete corresponding handoff, otherwise `ERROR` with the applicable reason and known paths. Keep the attempt best effort even when processing must throw a fatal ownership error. An explicitly missing one-shot HDR receives `ERROR`; stale watcher entries and deferred candidates receive no terminal email-log record.

Return `Deferred` before any ownership move, routing lookup, or retained-error diagnostic; produce no `.hdr.sort`, `.sort.err`, or terminal email-log record. With `-v`, emit `DEFER` including reason and source paths. The ordinary watch loop continues and later scans reconsider final EML candidates, including after input notifications or its 30-second idle scan. `HDR_WRITING` is quiet on watch-mode stderr; `HDR_STATUS_UNEXPECTED` reports each encounter, even without `-v`. One-shot mode prints `NOT READY` and returns 1. Unknown or incomplete statuses may remain deferred indefinitely for manual investigation; never promote or rewrite them. Do not add per-message sleeps, a retry loop, a timeout, or automatic recovery of suffixed files.

Completed `UPSTREAM_FAILED` retention still returns `MessageOutcome.Failed`, one-shot exit 1, and watcher continuation. Attempt exactly one terminal `ERROR` with reason `UPSTREAM_FAILED`, actual current paths, and the attempted retention target; a retention I/O failure retains that reason and adds its operation/error. Attempt stderr in all cases. Attempt `<basename>.sort.err` beside the current owned HDR: in `failed` after both moves, or in Proc after directory creation, first-move, or second-move failure. The second-move failure leaves a split pair. Attempt retention before best-effort diagnostic/email-log output so their failure cannot prevent it. Never open EML contents, rewrite status bytes, overwrite, delete, roll back, retry, or release failed mail. No startup dependency on `failed` or `senders/sender-ids` is introduced; the holding directory is created only after ownership of a confirmed upstream failure.

**VERSION-SENSITIVE-001:** A visible plain HDR is not a producer-completion trigger and can exist for an attempt that never publishes an EML. Final EML visibility starts discovery; it does not by itself establish matching HDR readiness. `File.ReadAllBytes` opens the HDR with `FileShare.Read`, which excludes an existing writer even when that writer permits readers. Keep that sharing behavior: allowing write sharing would permit reading an unfinished HDR. Its handle closes before claim, so it does not prevent a later producer reopen. The required producer contract is that, once final EML exists and this read returns a `Written` HDR, both files are complete and no later producer write/reopen changes them. Saved successful build 9742 SMTP and immediate/delayed/scheduled REST originals had `Written `; failed originals had `Failed `. This is bounded evidence, not a universal route guarantee. See the [historical sequencing report](live-sequencing-2026-09-16.md) and [positive-status contract note](written-readiness-2026-09-17.md). Every deployment route still requires current evidence. The tagger still discovers plain HDRs from our EML-first/HDR-last handoff. Keep the existing literal filename-component validation; the paired basename does not acquire a numeric-only requirement.

The auth lookup is a simple read-only directory lookup. Apply the literal-component predicate before constructing an address-derived path. For an enrollable auth, establish that `senders/auth-addresses` is accessible and a directory, then call `File.GetAttributes` for the one canonical child. Under the stopped-administrator trust rule, `FileNotFoundException` or `DirectoryNotFoundException` for that child means absence; an existing non-directory or any other exception means `Hold`. The trusted administrator and enforced sorter singleton mean no handle-relative lookup or race-reconciliation layer is needed.

After ownership, catch message-local failures, write the best available `.sort.err` beside the current owned HDR, and continue with later messages. Upstream-failure retention errors are message-local, including destination collisions, and retain the exact partial state. A failure to make the HDR inert is process-fatal because the sorter cannot safely continue past the selected live trigger. With final EML present, a missing HDR before ownership is a stale result only in watch mode; in one-shot mode it means the requested message did not complete and returns nonzero. A retained plain EML beside `.hdr.sort` has no matching plain HDR and is skipped as stale; the scan never promotes or rereads the retained header.

## 8. Tagger implementation

### 8.1 Startup

After acquiring both tagger locks in the order above and attempting requested datadir logging, enumerate the [required configuration roots](storage-reference.md#required-directories-and-creation), then load all sender-id records, auth indexes, and live mappings. Apply the [sender-configuration checks](storage-reference.md#sender-configuration) and [mapping-record checks](storage-reference.md#persistent-tag-mappings), including the referential relationships that affect sender-id record selection or mapping uniqueness. Do not require or inspect tag logs. Parse each template once under its stored-format rules; validate its fixed bytes and placeholder position so every token from the permitted alphabet yields a canonical usable tag address. Trust `ASSUMPTION-TEMPLATE-LENGTH` rather than adding a transport-length gate. Ignore unrelated extra files. After successful validation, create the mailroot process directory if needed. Report inert data staging and process-queue message leftovers, including `.hdr.err`/`.eml.err`, but do not act on them. Never fall back to or migrate earlier datadir mail directories.

Store parsed templates, configured private addresses, auth-index bindings, and MDN policy in the immutable startup snapshot. Do not reread them per message. Former auth/private metadata files are unrelated extras; do not parse them, derive an inactive account state from them, or add a fallback reverse-list lookup.

### 8.2 Message processing

For each selected plain HDR:

1. Claim the HDR as `.hdr.start` and then the EML as `.eml.start`; optionally copy `.in` evidence after both moves succeed. A non-stale first move failure is fatal, while a failure after HDR ownership is message-local.
2. Parse the complete HDR framing plus its metadata and supported HDR sender occurrences once, resolve auth against the startup configuration, and select the current sender-id record. Retain recipient line 3 as an uninterpreted byte range; do not parse recipients yet.
3. Parse every supported EML sender-field occurrence syntactically. Invalid or ambiguous syntax within any occurrence is an immediate message failure before a no-match pass-through decision. Record `From:` occurrences with their mailbox counts and `Reply-To:` occurrences, but defer the activated-message count checks; individually valid occurrences are allowed to pass unchanged when no current-private match exists.
4. When the sender-id record has `allow-mdn=false`, classify top-level Content-Type. Malformed classification syntax is a message failure, and a recognized MDN fails closed before recipient parsing or tag lookup. When the flag is true, skip classification because it cannot change the outcome.
5. When no field matches the configured private-address, optionally create the parent `.out` copies and then move the unchanged `.eml.start` and `.hdr.start` to the spool in that order. Former private addresses have no special state and follow this same non-match rule.
6. On a configured-private match, require exactly one EML `From:` occurrence containing exactly one mailbox and at most one `Reply-To:` occurrence, before recipient parsing, tag lookup/allocation, or child creation. For a `From:` count violation, rename the owned HDR from `.hdr.start` to `.hdr.err`, then the EML from `.eml.start` to `.eml.err`, with `File.Move(..., overwrite: false)`. A failed retention move stops further retention moves; preserve exact residual paths and never roll back or overwrite. Attempt the parent `.err` diagnostic, an optional trace error event, and standard-error output regardless of `-log`; none of their failures releases the rejected mail. Repeated `Reply-To:` remains a message-local error in `.start`. Apply these checks regardless of the matching sender field or group handling. On success, retain the validated `From:` without reparsing, then move the parent HDR and EML from `.start` to `.break` in that order. Only now parse and canonicalize recipient line 3. Construct each child as EML and HDR `.process` files; after both are complete and closed and their edited/synthesized EML header lines pass §8.1 of `spec.md`, move the EML and then HDR to `.pend`. A header-length contract error stops construction before publication, retains the `.break` parent and any inert child files as they stand, and attempts the parent `.err`, requested trace error event, and standard-error output regardless of `-log`.
7. When `-keep` is enabled, create every child `.out` copy before any publication.
8. Publish children sequentially in canonical order, attempting every referenced tag log immediately before the child's EML move. Report a logging failure to standard error and continue the remaining log attempts and that child's EML/HDR moves in order. When file tracing is available, attempt tag-log result and EML-move intent events between those operations; their failure cannot stop publication.
9. After every child HDR is live, delete the parent EML and HDR. `File.Delete`'s already-absent success is the desired idempotent cleanup behavior.

Keep the code aligned with the state names in the specification. A small per-message state object may track current filenames and child statuses for diagnostics; do not create a generic workflow engine.

### 8.3 Mapping creation

On a map miss:

1. Create one complete inert staging identity record. Attempt the optional empty tag log separately; its failure only prints to standard error.
2. Generate the CSPRNG bytes for one token and map each byte's low five bits into the [tag-token alphabet](storage-reference.md#identifiers-and-addresses).
3. Substitute the token into the first `%` in the validated template and form the canonical tag address.
4. Move the staging directory to the final tag-address name without replacement.
5. If `Directory.Move` throws `IOException`, inspect only that proposed final path. Under the singleton and stopped-administrator rules, an existing final directory identifies the specified tag-token collision; generate another token and retry, up to sixteen proposals. If it does not exist, rethrow the publication failure. Let every other exception propagate. Do not preflight the destination before the move.
6. After publication succeeds, insert the mapping into the in-memory dictionary.

Construct the dictionary key before publishing. If insertion unexpectedly cannot complete after publication, stop the tagger so restart can reload the live mapping; do not continue with an authoritative in-memory map that omits it.

## 9. Errors and diagnostics

Define a few domain exceptions or result types only where they clarify the specified boundary:

- startup/configuration failure;
- sorter message failure;
- tagger message failure;
- fatal watcher/singleton failure.

Do not wrap every framework exception. At the message boundary, add the basename, current state, and relevant path/operation before attempting the diagnostic. A `From:` contract error uses the specifically defined `.hdr.err`/`.eml.err` retention path and must also be reported to standard error and the requested trace when available. An output-header-length contract error retains the normal `.break`/inert-child states and reports the child, field, physical-line position, measured length, limit, and retained paths through the parent `.err`, requested trace, and standard error. At the executable boundary, print the complete exception chain to standard error and return nonzero when the specification classifies the underlying failure as fatal. Catch logging and diagnostic-file failures within their output paths, report them to standard error, and preserve the underlying mail outcome.

The tagger's optional execution trace records decisions and state transitions, not every local variable or framework call. Before a persistent mutation, attempt an intent event containing the operation and expected state change. After it returns, attempt its success/failure and known resulting state. These attempts are best effort and never gate the operation. The two specification exceptions are intentional: never recursively log `log.txt`'s own writes, and do not log `-keep` copy operations. Use ordinary operation names such as `move`, `create`, `append`, `copy`, and `delete`; include the managed exception type, HRESULT, message, and paths when useful. Never report a state that is not known. Sorter `-v` provides its separate console debugging; sorter `-l` contains only terminal message records.

Do not add automatic retries except for explicitly specified tag-address collisions. Do not roll back a moved EML, automatically resume residual work, or clean inert evidence.

## 10. Testing approach

Testing should establish behavior without forcing production code into a simulation framework.

- Unit-test canonicalization, recipient-id encoding, bounded parsers, MDN classification, edit planning, rewriting, child ordering, and routing decisions with byte fixtures.
- Verify that activated messages with missing or repeated `From:` fields, including differently cased field names, or multiple `From:` mailboxes retain `.hdr.err`/`.eml.err` before tag lookup/allocation, attempt the parent `.err` and optional trace, and print to standard error. Cover partial retention-move failures, single- and multi-recipient messages, existing and absent `Reply-To:`, and activation solely through another sender field. Also cover a valid single-mailbox `From:` and unchanged no-match pass-through behavior.
- Verify the output-header-length boundary at 998/999 bytes, including synthesized field-name growth, changed continuation lines, and folded fields whose total length exceeds 998 while each checked physical line fits. Verify that unchanged physical lines, removed fields, opaque headers, bodies, HDR files, and no-match pass-through are outside the check. A later-child length failure must publish no children, retain parent/child evidence, preserve new mappings for reuse after restart, and report diagnostics without releasing the message even when logging fails. Never refold output to make the check pass.
- Inject clock and randomness where deterministic values matter.
- Test sorter and tagger state transitions against isolated temporary directory trees using real `System.IO` operations.
- Test singleton contention and `FileSystemWatcher` behavior as Windows integration tests rather than emulating every internal operating-system result.
- Test exceptions at meaningful application boundaries. Do not require an injectable wrapper around every `File`, `Directory`, or `FileStream` call solely to manufacture impossible native return combinations.
- Verify that missing/inaccessible tag logs do not block startup or mapping reuse; empty-log creation and append/encoding/flush/dispose failures do not block mapping allocation, the same child's publication, later children, parent cleanup, or a successful one-shot exit. A failed requested trace disables only that trace for the invocation. Malformed bytes and partial tails are accepted without alteration. Verify standard-error reporting, including when logging fails while reporting a real `From:` contract error.
- Verify sorter `-l`/`-v` independently and together, exact terminal records and stale-entry suppression, escaped output, partial handoff paths, and the fatal ownership/missing one-shot outcomes. Fail email-log formatting/open/append/flush/dispose and debug stdout separately; preserve the same message result and later processing, without parent creation or automatic retry. Exercise the CLI ordering and both published distribution forms without introducing tagger-only dependencies.
- Run black-box tests against the exact release executables.
- Keep real SmarterMail, DNS, SMTP capture, DKIM/DMARC, client, and provider verification in the external laboratory described by `testing-plan.md` and `assumptions.md`.

Important residual states and failures must still be exercised. “Do not be overly defensive” narrows the assumed world; it does not excuse missing tests for malformed mail, real I/O errors, partial publication, or process termination between documented transitions.
