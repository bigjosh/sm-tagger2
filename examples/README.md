# Configuration example

`datadir/` contains one complete synthetic sender-id record and two active auth indexes, `auth@example.com` and `alias@example.com`, pointing to that same ID. They demonstrate shared private identity, template, MDN policy, and recipient tags. It contains no actual-server sample data and cannot be used as a production account configuration. The authoritative [runtime layout](../storage-reference.md#runtime-directory-trees) and [sender-configuration reference](../storage-reference.md#sender-configuration) define the paths, required files, encodings, and contents.

Before enabling a new sender, choose its permanent sender-id under the [identifier rules](../storage-reference.md#identifiers-and-addresses) and generate a non-public private alias with cryptographically secure randomness. The example uses a UUID, but a descriptive name is equally valid. Replace the example sender-id directory and both index pointers together, preserving exactly the same spelling in all three places. Rename each auth-index directory to the intended canonical authenticated address, or omit the unused example index; every published directory enrolls its named account. No auth file exists in the sender record. Check the complete record against the reference. Existing installations must follow the [offline conversion procedure](../sender-configuration-2026-09-17.md); do not rename their established IDs or replace their data with this example. The [sender-ID upgrade note](../README.md#sender-id-upgrade) explains why no conversion is needed for existing IDs and why older binaries cannot read new descriptive IDs.

Provision the private alias as an authorized sending identity on every account sharing the sender-id, choose a dedicated reserved tag domain with the required catch-all, and replace the example template using the [sender-configuration format](../storage-reference.md#sender-configuration). Keep `allow-mdn.txt` at `false` until its evidence gate passes for every account and path sharing the record.

Perform all sender-id record/index edits while affected submissions are paused and the tagger is stopped. Build an auth-index directory completely under `senders/auth-addresses/.staging/` and publish it directly under `senders/auth-addresses/` with a non-replacing same-volume directory move. Repeat with another canonical auth directory pointing to the same sender-id to share the private identity, template, MDN policy, and existing tags; restart before using the added account. Every published index is active. Removing one makes future sorter mail pass as unenrolled, while unknown already queued auth fails closed after restart. Keep sender records and mappings even when their last index is removed.

Use [bring-up.md](../bring-up.md) for sorter-only and empty-tagger trials before enrolling this sender; [required directories and creation](../storage-reference.md#required-directories-and-creation) distinguishes the two stages. Neither executable detects, migrates, or falls back to an earlier layout.

Do not create permanent tag mappings by hand; the runtime creates them during allocation. Mail and data locations follow the [current storage reference](../storage-reference.md#runtime-directory-trees); current installations also need the [offline mail-queue migration](../queue-layout-2026-09-17.md) when upgrading. SmarterMail routes, signing, catch-all delivery, and client compatibility retain their deployment gates. The owner-confirmed Proc-subtree isolation assumption is accepted for the new mail workspace, without claiming a fresh live test. See [deployment.md](../deployment.md), [spec.md](../spec.md), and [assumptions.md](../assumptions.md).
