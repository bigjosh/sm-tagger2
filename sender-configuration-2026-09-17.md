# Sender configuration — rc.9 conversion

**Version scope: rc.9 configuration conversion.** These configuration decisions remain necessary when upgrading from earlier versions, but rc.10 also relocates mail working state. Follow the [current queue migration guide](queue-layout-2026-09-17.md) for coordinated backup, mail paths, lock ownership, and cutover. Perform this guide's configuration edits offline without its intermediate restart step; its earlier datadir-mail backup description does not include an rc.10 mailroot.

Local candidate **1.0.0-rc.9** makes the published auth index authoritative. Several authenticated accounts can point to one sender-id and share its private-address, template, MDN policy, and existing recipient tags. A sender-id record with no auth indexes remains valid, so historical mappings can be retained without enrolling an account. The current paths and file formats are defined only in [storage-reference.md](storage-reference.md#sender-configuration); [spec.md §1.2](spec.md#12-authenticated-enrollment-and-the-private-address) defines the resulting behavior.

This change removes `auth-address.txt`, `retired-auth-addresses.txt`, and `retired-private-addresses.txt` from the runtime configuration. The programs do not read or validate them, even if old copies remain. There is no primary auth account, reverse auth list, or retired runtime identity state. An old private address becomes an ordinary non-match after replacement and may pass through unchanged. Removing an auth index makes later sorter lookups pass that account as unenrolled; an already queued auth absent from the restarted tagger's snapshot still fails closed.

**Former retired auth indexes need an explicit decision before cutover.** They used to divert mail into a retired-auth rejection. Under rc.9, every index left published is active. Keeping an old retired list does not prevent this. Remove such indexes offline unless you intentionally approve those accounts for active shared enrollment. If an account must be prevented from sending, disable that path upstream; deleting the index alone permits ordinary sorter pass-through.

## Offline conversion

1. Pause affected sender submissions, upstream SmarterMail processing, and administrative configuration changes. Stop both sorter and tagger and confirm their owning processes have exited. Record the actual data/spool roots, launch identities/arguments, and hashes of both old binaries. No live server data is moved by preparing this document.
2. Make and verify a **complete protected backup** of the datadir while all writers remain stopped. Preserve file inventories, bytes, required permissions, stable UUIDs, all auth indexes and former metadata, permanent mappings, both staging trees, queued/retained mail, and logs. Proc and the normal spool are outside this backup; inventory and preserve their states separately. Keep the prior binaries and their hashes. Do not replay or rename message-state files during conversion.
3. If the installation predates the nested layout, perform only the offline directory moves from the [rc.8 layout procedure](sender-layout-2026-09-17.md), preserving every original byte. Do not follow its intermediate restart step. Continue this conversion with both programs and upstream processing still stopped.
4. Inventory every published auth index and its pointer. Compare it with the old current/retired metadata in the backup, and record an explicit disposition for each account: retain as active, intentionally activate a former retired account, or remove enrollment. Resolve missing pointers, unknown target records, or inconsistent old metadata before continuing; do not infer enrollment from obsolete files.
5. Move every index selected for removal, as a complete directory, into a new protected conversion archive **outside the live auth root and both staging roots**. Use verified absolute paths and non-replacing moves; stop and preserve exact partial state if any operation fails. Never overwrite or discard an existing archive. Indexes retained as active must each point to the intended existing sender-id. Multiple indexes may share that ID. Do not regenerate UUIDs or delete records with no remaining indexes: their mappings remain permanent.
6. Move the three obsolete metadata files from each working sender record into the protected conversion archive, preserving their sender association and bytes without replacement. Validate the remaining record and all active indexes against the [authoritative configuration rules](storage-reference.md#sender-configuration). Do not rewrite private-address, template, MDN policy, or mapping identity bytes merely for this conversion. Extra obsolete copies would be ignored, but leaving them in the working tree can mislead an operator about protection that no longer exists.
7. Reconcile affected queued mail and client settings before restart. A message already in `process` for an index removed from the new snapshot will fail closed; new mail from that unenrolled auth may pass unchanged. Former private identities have no special rejection. Record the intended disposition of queued messages without automatically replaying held inputs. Prove the shared private alias is authorized on every retained/added account and that all routes have the required signing and delivery evidence. Keep the shared MDN flag false unless its approval covers **every account and every capable path**, including newly added ones.
8. Verify the final inventory against the backup and recorded conversion decisions. All stable sender IDs, permanent mapping identity files, tags, and retained message bytes must be unchanged. Check permissions and confirm there are no partially converted pointers or unintended active indexes. Preserve all archive/backup evidence. Deploy **both matching rc.9 binaries together** and update scheduled, wrapper, and manual launch paths together; do not mix old and new configuration semantics.
9. Retain a post-conversion checkpoint before processing resumes. A watcher startup is not a read-only configuration check: it can immediately process backlog. Start the matched programs only after queued-mail decisions are complete, then resume the approved submission paths and verify fresh controlled mail. For two accounts sharing an ID, confirm the same canonical recipient reuses the same existing tag across accounts and restart. Keep all broader [deployment gates](assumptions.md) pending until their actual evidence is recorded.

## Rollback

Before any post-cutover mail or mapping/configuration state is created, stop both programs and upstream processing and restore the complete prior backup plus both prior binaries and launch paths. Restore the prior configuration meanings as well as its directory layout; the archived old metadata is not optional for old versions. Do not overlay old files onto a partially converted tree or overwrite uncertain evidence.

After any new post-cutover state exists, rollback requires offline reconciliation first. Preserve every new mapping, tag-log append, configuration change, queue transition, and retained artifact; establish whether any output may already have been delivered. Restoring an old backup without that reconciliation can lose permanent tags or duplicate mail. Neither executable infers or performs this recovery. Keep the system paused if a complete disposition cannot be established.

## Verification scope

This is an operator conversion procedure, not evidence that an actual server has been migrated. Current build, automated-test, and artifact results are recorded in [validation-report.md](validation-report.md). Earlier rc.8 layout and rc.7 readiness reports retain their original scope and do not prove the rc.9 semantic conversion or shared-account deployment behavior. No new live SmarterMail compatibility result is claimed by this document.
