# Build and deployment

Version 1 provides two Windows console applications. Local automated tests cover the program contract; an actual SmarterMail deployment remains subject to the evidence gates in [assumptions.md](assumptions.md) and [testing-plan.md](testing-plan.md).

[storage-reference.md](storage-reference.md) defines the directory layouts and file formats; [spec.md](spec.md) defines behavior. This document covers building, deploying, and operating the executables.

For the required folders and commands at each stage, start with [bring-up.md](bring-up.md). It begins with an empty enrollment index and sorter-only pass-through before introducing tagger sender-id records. Local rc.17 adds startup information to independent [concise console output](README.md#concise-console-output), retaining sorter `PASS`/`TAKE`/`FAIL` labels, rc.14 [child naming](README.md#child-naming-upgrade), rc.13 [configuration and diagnostics allowances](README.md#configuration-and-diagnostics-upgrade), descriptive sender IDs under the [identifier rules](storage-reference.md#identifiers-and-addresses), rc.11 logging, the rc.10 Proc mail workspace, and rc.9 enrollment semantics. Existing IDs need no conversion; consult the [sender-ID upgrade note](README.md#sender-id-upgrade) before introducing new IDs or considering older binaries. For an installation predating rc.10, complete the [offline queue migration and rollback procedure](queue-layout-2026-09-17.md) with both programs stopped and upstream processing paused. That guide includes earlier configuration conversions when needed; there is no fallback or automatic migration.

## Build and verify

Install the .NET 10 SDK selected by [global.json](global.json), then run from the repository root in Windows PowerShell 5.1 or PowerShell 7:

```powershell
dotnet restore SmTagger.slnx --locked-mode
dotnet build SmTagger.slnx -c Release --no-restore
dotnet format SmTagger.slnx --verify-no-changes --no-restore
.\scripts\Publish-Release.ps1
dotnet test SmTagger.slnx -c Release --no-build --no-restore
```

`scripts/Validate.ps1` runs that complete sequence and writes a TRX report under `artifacts/test-results/`. Tests use isolated temporary directories. Three optional sample tests run when the private `samples/` folder exists and otherwise report explicit skips. Release process tests report explicit skips until both production executables have been published. The complete validation script publishes them before testing.

If Windows PowerShell blocks these locally created scripts under its default execution policy, a process-scoped invocation is `powershell.exe -NoProfile -ExecutionPolicy RemoteSigned -File .\scripts\Validate.ps1`. This does not change the machine's saved execution policy. Organizational policy still takes precedence.

The test dependency versions are locked in `tests/SmTagger.Tests/packages.lock.json`. Production code uses the .NET base class library. Unit tests may use narrow internal phase, stream, clock, or randomness seams; the production programs provide no command-line, environment, configuration, or message-controlled route to those seams.

## Release files

Download release assets from [GitHub Releases](https://github.com/bigjosh/sm-tagger2/releases), or run `scripts/Publish-Release.ps1` to build them locally. Both distribution forms target Windows x64 and include their .NET runtime, so the mail server needs neither an SDK nor a separate runtime installation.

Choose the standalone or complete-folder distribution from the [release inventory](storage-reference.md#release-and-repository-trees). Verify the supplied manifest hashes before running it. Copy both standalone EXEs, or extract/copy each application folder intact; an application-folder EXE cannot be deployed on its own. Retain the supplied runtime licenses and notices.

For the rc.14 child naming upgrade, stop the tagger and wait for its current work to finish before replacing its binary. Configuration and permanent mappings need no migration. Keep any older retained or partially published messages under their actual filenames; do not rename or replay them to apply the new format. Update filename-dependent tooling and follow the [upgrade note](README.md#child-naming-upgrade).

Earlier tested .NET 10.0.11 standalone builds used the runtime inside the executable; local host tracing and execution observed no extracted runtime files. See [validation-report.md](validation-report.md) for the tested scope. This does not establish the behavior of every future runtime build or deployment host.

Windows Application Control initially blocked the local rc.6 standalone sorter before startup, producing 14 launch failures alongside 441 passes and zero skips. After the user disabled Smart App Control, the same unchanged binaries passed all 455 automated tests with zero failures/skips. Compatibility with Smart App Control enabled remains unverified. The three live SM scenarios used the application-folder distribution; they were not repeated during this policy retest. The [retention report](failed-retention-2026-09-16.md) preserves both automated runs. Artifact verification confirms bytes, not permission to launch; verify the selected distribution under the intended host policy and identity. The testing agent changed no security policy, certificates, code, or binaries for the retest. A script execution-policy option does not resolve an executable launch block.

Some bundled runtime versions may extract native components before startup under the process account's `%TEMP%\.net`, or under `DOTNET_BUNDLE_EXTRACT_BASE_DIR` when set. If extraction is required, the account needs a writable location protected from other accounts. Verify startup and any extraction under the actual scheduler/wrapper identity for the selected release (`LAB-013`); [Microsoft's single-file deployment documentation](https://learn.microsoft.com/en-us/dotnet/core/deploying/single-file/overview#native-libraries) describes the extraction behavior when used.

The publish script recreates generated output directories. Keep configuration, mail, and operator evidence outside them. The sorter includes no tagger-only parsing or mapping assemblies in either distribution. Republishing with a supported SDK servicing update also updates the bundled runtime.

The local build host is Windows 11, not the target Windows Server installation. Test the selected release assets and record their manifest hashes on the actual supported Windows Server and SmarterMail builds before enabling production mail flow. Release candidates remain subject to the pending deployment gates in [assumptions.md](assumptions.md).

## Prepare the data and spool trees

For sorter-only pass-through, create an empty, accessible `<datadir>\senders\auth-addresses` directory. The existing spool root and its `proc` directory must be ready before startup. `senders\sender-ids`, `process`, and mapping directories are not needed for that stage. Unfinished input stays untouched; malformed or ambiguous completed HDRs still fail closed.

Before starting the tagger, prepare both nested sender roots using the [required-directory checklist](storage-reference.md#required-directories-and-creation) and [sender-configuration reference](storage-reference.md#sender-configuration). Follow [examples/README.md](examples/README.md) to adapt the synthetic example, replacing its example identities and choosing the permanent sender ID before real use. A UUID is optional; preserve exact sender-ID spelling across the directory and pointers. The tagger rejects incomplete or inconsistent live identities and mappings at startup, but records with zero indexes are valid and preserve mapping history. [bring-up.md](bring-up.md) supplies the staged commands; the reference identifies which working directories the programs create. For shared sender IDs, establish identity authorization, signing, routing, and the MDN gate separately for every enrolled account and path.

The operator must configure every intended SmarterMail submission path to enter the selected `<spooldir>\proc` queue. SmarterMail invokes neither program. Use the [runtime placement rules](storage-reference.md#runtime-directory-trees): Proc, its fixed mailroot, and spool output share one ordinary local NTFS volume without junctions; data/mapping storage may use another NTFS volume, with its staging and final mappings together. The owner confirms SM does not read the Proc tree; rc.10 accepts that isolation assumption for the nested workspace without claiming a new live retest. The sorter scans only top-level Proc entries. The programs trust placement and permissions without new preflight. Failed retention remains lazy; apply intended permissions to both mail and data trees, including unredacted diagnostics.

Verify SmarterMail's producer readiness behavior separately from our EML-first/HDR-last publication. HDR can precede EML and can exist for an attempt that never produces one; the tested direct API route with `sendImmediately: true` instead created EML first. Ordinary browser Send and delayed-send publication were not traced in that test set. The current sorter retains the rc.7 readiness rule: it discovers final EML, reads the matching HDR with read-only access and `FileShare.Read`, and requires exact `Written` before classification. Its read handle closes before ownership. `Failed` retains the existing error path; `Writing` and unexpected/incomplete statuses defer. Establish on every installed route that a successfully read `Written` HDR plus final EML means both files are complete and receive no later producer edits (`LAB-001`); none of these checks proves a universal producer guarantee. [Historical build 9742 evidence](live-sequencing-2026-09-16.md) and the [current status contract](written-readiness-2026-09-17.md) record the scope. Also verify admission limits, basename namespace, arbitrary new tag acceptance, post-rewrite aligned DKIM/DMARC, SPF for changed envelope domains, and catch-all delivery. Keep MDNs disabled until every permitted sender/client path has its required evidence. The `VERSION-SENSITIVE-*` markers beside dependent source code identify checks to repeat after updates.

## Run

Start each watcher independently, supplying your approved paths. These examples place the standalone EXEs together in `D:\sm-tagger-bin`; for application-folder deployments, include the corresponding `sm-sorter` or `sm-tagger` subdirectory:

```powershell
& 'D:\sm-tagger-bin\sm-sorter.exe' 'D:\sm-tagger-data' -l 'D:\sm-tagger-data\sorter-mail.log' -c 'D:\SmarterMail\Spool'
& 'D:\sm-tagger-bin\sm-tagger.exe' 'D:\sm-tagger-data' -l 'D:\sm-tagger-data\tagger-trace.log' -c 'D:\SmarterMail\Spool'
```

Each command is a long-running console process; use separate consoles or independently supervised jobs. These are not native Windows services. A host must capture standard error and use a supported Ctrl+C/Ctrl+Break console event for orderly shutdown; terminating the process otherwise has crash semantics. Capture each program's standard output too when `-v` or `-c` is enabled. Task Scheduler/service-wrapper behavior still needs verification on the chosen deployment host.

Sorter `-l <logfile>` records one terminal result per processed message; see the [log format](storage-reference.md#logs-and-diagnostics). `PASS` means unchanged publication to the spool completed; `DIVERT` means handoff to the tagger queue completed; `ERROR` means sorting failed. These are sorter outcomes, not delivery receipts. Lifecycle events and readiness deferrals receive no email-log record. An explicitly requested missing one-shot HDR does get an `ERROR` record.

Sorter `-v` independently writes lifecycle, scan, routing, and file-operation debugging to standard output. Tagger `-l <logfile>` saves detailed execution-trace events; tagger `-v` independently prints those events with a `DEBUG ` prefix to stdout. Errors always go to stderr. Put each program's options after the datadir and before the spooldir, in any order and at most once each. Prefer absolute log paths; relative paths resolve against the process working directory. Create each log's parent directory yourself and use distinct dedicated files outside mail queues, configuration, and mapping records. Protect the unredacted output. There is no automatic parent creation, rotation, truncation, repair, or retry for these logs.

Use `-c` for startup information followed by one console line after each complete output-pair move. Startup shows the program/version, selected mode, and resolved data/spool paths after the required locks. The tagger then reports the sender records and all individual/group mappings successfully loaded from disk, before queue processing; the sorter does not load or count them. Counts exclude inert staging and are not updated after later tag allocation. The welcome says `starting`, not ready; configuration/mapping failure can follow it on stderr without a load summary. The sorter reports the original basename followed by `PASS` for `spool`, `TAKE` for `process`, or `FAIL` for `failed`, with no trailing destination clause; the tagger reports each published child with its individual created/used tag, or an unchanged pass-through parent. See the [concise format](storage-reference.md#concise-console-output--c) for original HDR envelope fields and server-local timestamps. Deferred, stale, partial, or failed moves produce no concise summary; existing stderr remains available. Completed `Failed` retention produces a concise `FAIL` line while keeping the existing error outcome. The per-pair lines confirm transfer, not final delivery.

`-c` and `-v` have no precedence: supply both to emit both. `-c` changes neither selected file logs nor mapping logs, including their UTC timestamps. The rc.17 startup display and rc.16 sorter format change require only stopping and replacing the executables, without a storage conversion. Binaries predating rc.15 reject `-c`. Add `-v` to the examples above when detailed console tracing is wanted.

Update all previous tagger `-log` launchers to `-l <logfile>` before using rc.11 or later; the old flag is rejected. There is no default datadir trace path. `-keep` is unchanged. See the [CLI upgrade note](README.md#tagger-cli-upgrade); an rc.10 installation needs no storage conversion for this option change. Include external log locations in protected backups independently of data/mail roots.

For a controlled one-shot test, append the exact plain-message basename. Tagger options appear immediately after the datadir. A leading dash in the basename is allowed. One-shot execution cannot overlap a watcher of the same role. `-keep` retains parent `.in` and final `.out` evidence. The source EML body and unsupported headers are always preserved.

The sorter scans final `.eml` files and checks the EML before any HDR access. An HDR-only attempt remains untouched; a selected EML that disappears is stale in watch mode. Interpret status bytes using the authoritative [message-file format](storage-reference.md#message-files). Exact `Written` permits classification; malformed remaining HDR data still holds as `UNSAFE_HDR`. `Writing` defers with `HDR_WRITING`, quietly on watch-mode stderr. Every other or incomplete status except `Failed` defers with `HDR_STATUS_UNEXPECTED` and reports unexpected status to stderr on every encounter regardless of flags, without deduplication. All deferrals, including missing EML in one-shot mode or HDR sharing/lock conflict, leave mail unchanged, perform no auth lookup or EML-content read, and create no `.hdr.sort`, `.sort.err`, or terminal email-log record. With `-v` they produce `DEFER`. Watch mode reconsiders candidates through normal scans; one-shot reports `NOT READY` and returns 1 without waiting. An unresolved status may persist indefinitely for manual investigation; never promote it or rewrite it.

Exact `Failed` keeps the prior outcome and move order at the rc.10 location: claim `.hdr.sort`, lazily create `<mailroot>\failed`, then move EML first and the still-suffixed HDR last there without replacement. Complete retention is still a failed mail outcome: one-shot returns 1, watcher continues, stderr reports it, and the optional log receives one terminal `ERROR` with actual paths. The [historical retention evidence](failed-retention-2026-09-16.md) used the earlier datadir location. The tagger scans only `.hdr` files in the mailroot process queue; both roles publish EML first and plain HDR last. Observe queue age and investigate incomplete producer attempts manually. Neither executable falls back to or migrates old queues.

## Observe failures

For SmarterMail's outbound SMTP conversation, select its **Delivery** log and the relevant date; the **SMTP** log covers incoming connections. For the current child names, search the original parent basename with **Display Related Traffic** enabled to collect its children, once that lookup has been verified against receiver evidence and raw logs on the installed build (`LAB-015`). SmarterMail searches substrings, so a child-prefix search can also find longer child numbers; compare the actual filenames and sessions when narrowing results. Its shortened session IDs are not globally unique identifiers.

The [local outbound logging test](outbound-logging-2026-09-18.md) found a build 9742 viewer bug with the former hyphenated child names: Related Traffic returns no results for the tested child even though its raw conversation is complete, and can incorrectly combine that traffic with a numeric control session. For those names or any failed lookup, disable Related Traffic / choose Only Matching Rows, search the recipient or full child basename to find its bracketed session ID, then search that exact bracketed ID. “Bracketed” means the square-bracketed value at the start of a log line, such as `[313455-1]` in the historical test. Alternatively inspect the raw daily Delivery log. Detailed logging must have been enabled at the time to recover full conversations. An empty viewer search is not a reason to resubmit mail. Recheck raw-versus-viewer correlation after SmarterMail or queue-naming changes; the [filename experiments](basename-logging-2026-09-18.md) are bounded observations, not a vendor guarantee.

Logging is best effort. A sorter email-log, console-debug, concise-console, tagger trace, or tag-log failure does not change the mail outcome. File logging failures print to standard error and the same current message continues. A failed sorter email log or tagger trace file is disabled for the rest of that invocation while requested verbose output continues; a console failure disables only the affected verbose or concise output and leaves the file available; a later invocation may try again. Corrupt and missing logs are accepted. A successful operation may therefore have no log record, and even a successful sorter result does not prove delivery.

Mail-contract and processing errors retain inert files and attempt a parent diagnostic. Only confirmed `UPSTREAM_FAILED` moves to `failed`; other sorter holds remain in Proc. A failed retention operation is message-local and preserves completed moves, possibly leaving EML in `failed` and HDR in Proc. The `.sort.err` follows the current owned HDR and records actual paths, the failed target, and any I/O error; diagnostic/log failure never blocks retention. There is no rollback or fallback release. Activated `From:` count failures retain original `.hdr.err`/`.eml.err` pairs when both retention moves succeed. Other tagger failures retain the actual `.start`, `.break`, `.process`, or `.pend` states. Edited/synthesized header lines above 998 bytes reject the parent before any child publication. Publication errors may leave earlier children live and later children pending; use the parent diagnostic and exact paths to reconcile that state.

The programs never retry or repair retained mail or staging entries automatically. Restart loads complete permanent mappings and reports inert leftovers in the input queues; neither program watches or scans the failed directory, or migrates older Proc residuals there. Inspect and clean that directory manually. The sorter considers final EML candidates and the tagger considers plain HDR candidates. A plain EML beside only `.hdr.sort` has no matching plain HDR and is skipped as stale. A new matching plain pair alongside an old `.hdr.sort` is not a recovery path: the non-replacing claim still fails on that collision. Stop the relevant owners before administrative changes or disposition. Automated notification, inbound processing, and recovery remain deferred in [future.md](future.md).
