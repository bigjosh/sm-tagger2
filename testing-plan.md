# Test plan

This plan defines verification of [spec.md](spec.md) using the pure managed C# implementation described in [implementation.md](implementation.md). The solution, synthetic fixture corpus, automated tests, and published executables are present. Completed local results and their limits are recorded separately in [validation-report.md](validation-report.md); the case tables below remain the verification requirements, including deployment work still to perform.

Use the most recent stable SmarterMail and Windows Server releases at bring-up, then record their exact installed builds in [assumptions.md](assumptions.md). Every applicable `VERSION-SENSITIVE-*` result begins `PENDING`. Captured samples are test inputs; compatibility with their bytes alone does not establish support for a deployment. Follow [bring-up.md](bring-up.md) for the staged folder setup and operator checks.

## Harness and release artifacts

- Keep deterministic C# tests in [tests/SmTagger.Tests/](tests/SmTagger.Tests/) for parsers, canonicalization, recipient identities, classification, edit planning, child ordering, and mapping decisions. Use the same production code and synthetic byte fixtures; inject clock/randomness only at the small test seams described in the implementation guide.
- Exercise real managed `System.IO`, `FileSystemWatcher`, and lock streams in isolated temporary directories on local NTFS. Use meaningful I/O failures, destination collisions, and process termination. Do not create a second filesystem implementation or require native Win32 test hooks.
- Run [scripts/Validate.ps1](scripts/Validate.ps1) from the repository root to restore locked dependencies, build [SmTagger.slnx](SmTagger.slnx) in Release with the pinned SDK, verify formatting, publish both production executables, and run the tests. The TRX report is written under `artifacts/test-results/`. [scripts/Publish-Release.ps1](scripts/Publish-Release.ps1) produces self-contained Windows x64 folders, ZIP archives, standalone EXEs under `standalone/`, and a SHA-256 manifest under `artifacts/release/`. Use these production executables for black-box and deployment checks. Verify both distribution forms, including standalone EXEs copied into a directory with no companion DLLs.
- Production CLI, environment, configuration, and message data must provide no route to select fake storage, time, randomness, or faults. Run mail experiments only with controlled test accounts and destinations.

Three optional local compatibility tests read private captures from `samples/` without modifying the originals or copying them into repository fixtures or release artifacts. They report explicit discovery skips when the folder is absent and suppress private values in failure output. Published-executable tests also report explicit skips until both release executables exist; the complete validation script publishes before testing. Keep local fixture compatibility distinct from approval of a live server/client route.

The executable contracts are:

```text
sm-sorter.exe <datadir> [-l <logfile>] [-v] <spooldir> [<basename>]
sm-tagger.exe <datadir> [-log] [-keep] <spooldir> [<basename>]
```

Capture before/after directory inventories and exact HDR/EML bytes, exit codes, standard error, sorter stdout with `-v`, and its email log with `-l`. Hash untouched bodies and pass-through pairs. Logs are supplementary evidence: their absence, corruption, or failed writes do not prove mail failed. Inspect retained file states and the independent receiver for publication/delivery outcomes.

## Deterministic contract cases

| Case | Required checks |
|---|---|
| UNIT-001: Fast HDR classifier | CRLF/framing/final blank line; all metadata keys; absent, mixed-case, repeated, malformed, empty, and null auth; `NO_AUTH`/`VALID_AUTH`/`UNSAFE`. Prove sorter handling never opens EML contents or loads tagger profiles/mappings. |
| UNIT-002: Address and mailbox grammar | Supported bare/name-addr shapes, quoted/encoded display names, legal folding, all supported sender fields, repeated metadata, null-path forms and original-byte preservation. Reject unsupported/ambiguous individual field syntax even before a current-private match is known. |
| UNIT-003: Canonical identity | ASCII case folding, first-original-spelling retention, canonical recipient sort/deduplication, `%`/`;` codec round trips, malformed escapes, unsorted/duplicate loaded records, sender-id separation, stable individual/group reuse across messages and restarts. |
| UNIT-004: Trigger and pass-through | Current, retired, unknown, missing, and inconsistent auth in `process`; private and retired-private matches in every supported field; partial matches and null envelope sender. A no-match message remains unchanged and does not parse recipients or touch mappings. |
| UNIT-005: Activated `From:` contract | Missing `From:`, repeated fields including mixed-case names, and a multiple-mailbox `From:` produce the specified contract error before recipient parsing, tag lookup/allocation, child construction, or publication. Cover one/many recipients, absent/existing `Reply-To:`, and activation solely in another supported field. A single non-private `From:` mailbox is allowed when another field activates tagging. |
| UNIT-006: Nonactivated counts | Absent/repeated/multiple-mailbox `From:` and repeated individually valid `Reply-To:` do not independently block no-match pass-through. Malformed syntax within a present field still fails; retired matches and blocked MDNs still take precedence. |
| UNIT-007: Fan-out and edits | Every matching sender addr-spec changes and every nonmatching span stays exact. Remove complete `Return-Path:` fields; leave bodies, recipient fields, unknown headers, and signature fields untouched. Test all group `Reply-To:` branches, nonmatching mailbox preservation, canonical child numbering, one envelope recipient, and lenient address-based `notify:` filtering with zero/multiple matches. |
| UNIT-008: MDN classification | Case/order/folding/quoted parameters, both recognized media types, receipt requests, DSNs, absent/duplicate/malformed Content-Type, duplicate parameters, and disabled/enabled policy. With `false`, recognized MDNs fail before no-match pass-through or mappings. With `true`, skip Content-Type classification and follow ordinary trigger rules without body rewriting. |
| UNIT-009: Configuration and allocation | Required identity files, complete auth-index/profile correspondence, missing/orphaned/duplicate/retired values, template first-token syntax, missing mappings root, inert staging leftovers, CSPRNG token alphabet/collision retry limit, complete directory publication, and fatal inability to cache an already published mapping. Template address length is the accepted operator assumption, not a new runtime rejection test. |
| UNIT-010: Output header-line length | Check resulting edited physical EML lines and every synthesized `Reply-To:` line at 998/999 bytes excluding CRLF; include field-name growth, display names, whitespace, and continuation indentation. A folded field may exceed 998 bytes in total if every checked physical line fits. Check actual individual/group tag lengths. No refolding; unchanged physical lines, removed fields, opaque headers, bodies, HDR files, and no-match pass-through remain outside this check. |
| UNIT-011: Sorter input readiness | Check final EML attributes before any HDR read/probe, including one-shot mode. Missing EML is stale in watch mode and deferred untouched in one-shot mode; directory/other attribute failures hold. With EML present, missing HDR is stale in watch mode and `MISSING_HDR` failure in one-shot mode. After EML discovery, exact case-sensitive `Failed` on the first CRLF-terminated HDR line, with optional trailing SP/HTAB, produces `UPSTREAM_FAILED` retention and never passes/diverts. Other statuses remain opaque, including `Written`, `Writing`, `Quarantined`, and unknown values; no whitelist or numeric-only basename restriction. Malformed HDR framing with final EML follows `UNSAFE_HDR`. Windows HDR sharing/lock violations defer; other read failures retain their normal failure scope. Neither readiness nor debugging opens EML contents or tagger configuration. |

## Best-effort logging cases

Logging is never a mail-success prerequisite. Test against both fresh and existing mappings and confirm the **same current message/child continues** after a logging-only failure; checking only a later message would miss this contract.

- `LOG-001`: Without `-log`, the tagger never touches its `log.txt`, even when it is corrupt, absent, or inaccessible. Without `-l`, the sorter accesses no email log; without `-v`, it emits no debug output. The sorter has no implicit dependency on tagger logs, configuration, mappings, or EML contents.
- `LOG-002`: With `-log`, check new event formatting, escaped controls, sequence/context, and honest intent/result state. Fail open/write/flush/dispose at meaningful points: report to standard error, disable the file trace for the rest of that invocation, and continue the same mail operation. A logging-only failure does not change its success exit code.
- `LOG-003`: Accept absent, unreadable, malformed, or incomplete diagnostic log contents without invalidating a profile/mapping or blocking startup. Append new entries without reading, repairing, truncating, or adding recovery separators to existing bytes. A newly allocated mapping remains publishable when best-effort empty tag-log creation fails.
- `LOG-004`: For a child using individual and group tags, attempt each distinct tag-log append in ordinal tag-address order immediately before publication. Fail one append and verify standard error, remaining append attempts, and the same child's EML/HDR publication continue. Preserve any partial bytes. A later fresh message naturally attempts the affected tag log again.
- `LOG-005`: Fail parent diagnostic output and standard error as well as file logging. Preserve the underlying mail result and actual residual state; do not introduce recursive logging, a second fallback system, or an automatic repair attempt. A real mail/configuration failure still has its specified failure scope even if its diagnostic cannot be written.
- `LOG-006`: Sorter email-log records contain exactly one terminal `PASS`, `DIVERT`, or `ERROR` per completed processing attempt, with UTC timestamp, escaped basename/auth/reason, and actual known file locations. Cover no-auth, non-enrolled and enrolled routing, upstream `Failed`, unsafe completed HDR, unreadable enrollment, readiness-check failure, EML disappearance after ownership, partial handoff, explicit missing one-shot HDR when EML exists, and fatal HDR ownership failure. Suppress records for HDR-only attempts, readiness deferrals in either mode, stale watcher entries, and all lifecycle/scan activity. Append UTF-8 without BOM plus CRLF, preserve corrupt/partial existing bytes, and never read or repair old log contents.
- `LOG-007`: Fail sorter email-log formatting/open/append/flush/close, including a missing parent directory. Report to stderr, disable only that file for the invocation, and preserve the current message's result, later mail processing, and exit status. Verify no parent creation, rotation, retry, or recursive fallback; a later invocation may open the log afresh. Independently fail verbose console output without affecting mail or the email log.
- `LOG-008`: With sorter `-v`, verify stdout lifecycle, scans, `DEFER` readiness reasons/paths, routing decisions, file operations, stale-entry debugging, and shutdown; stderr still carries errors with or without either flag. Check upstream `Failed` rejection and the one-shot `NOT READY` diagnostic without a retained error. Other status values must not produce readiness warnings or a `Written` whitelist. Test `-l` alone, `-v` alone, both, and neither in one-shot and watcher modes, including the published executables. Confirm debugging adds no EML reads or tagger-only dependencies.

## Deployment laboratory

Run these cases on the exact release executables and installed deployment. Repeat the relevant cases for every sender/client/version/platform/submission path; record disabled paths rather than silently omitting them. Save protected captures and link results under the corresponding assumption IDs.

Prioritize untested normal-operation assumptions in Windows/.NET, the production executables, and SmarterMail using the stages in [bring-up.md](bring-up.md). Establish real queue/auth grammar, one end-to-end rewrite, unregistered-tag acceptance and signing, fan-out, and watcher operation before broadening failure exercises. Existing local failure coverage and retained-file contracts remain required evidence; rerun affected boundaries when changes or observations justify it, and leave manual disposition of failed files to the operator.

## Completion and reruns

Before marking a deployment supported, record applicable unit/integration/release results and complete each empirical assumption for the actual scope, or record an explicit disposition permitted by the specification. Record `ASSUMPTION-PRIVATE-PROVISIONING` during onboarding and preserve the accepted `ASSUMPTION-TEMPLATE-LENGTH` decision. Keep MDNs disabled until their separate evidence gate is met.

For later changes, use the stable assumption markers to select the affected laboratory cases and relevant C# regression tests. New failures or behavior changes return affected evidence to `PENDING`; passing tests for an older build do not approve a newer one. This plan does not implement automatic recovery, inbound lookup, MIME rewriting, native service integration, or monitoring from [future.md](future.md).
