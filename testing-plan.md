# Test plan

This plan defines verification of [spec.md](spec.md) using the pure managed C# implementation described in [implementation.md](implementation.md). The solution, synthetic fixture corpus, automated tests, and published executables are present. Completed local results and their limits are recorded separately in [validation-report.md](validation-report.md); the case tables below remain the verification requirements, including deployment work still to perform.

Use [storage-reference.md](storage-reference.md) for the canonical paths, persisted formats, and input grammar. The concrete names, bytes, and boundaries in these cases identify required assertions against that reference; they do not define alternative formats. In particular, use its [required-directory contract](storage-reference.md#required-directories-and-creation) for fixture setup and its [message-state suffixes](storage-reference.md#message-state-suffixes) for retention inventories.

Use the most recent stable SmarterMail and Windows Server releases at bring-up, then record their exact installed builds in [assumptions.md](assumptions.md). Every applicable `VERSION-SENSITIVE-*` result begins `PENDING`. Captured samples are test inputs; compatibility with their bytes alone does not establish support for a deployment. Follow [bring-up.md](bring-up.md) for the staged folder setup and operator checks.

## Harness and release artifacts

- Keep deterministic C# tests in [tests/SmTagger.Tests/](tests/SmTagger.Tests/) for parsers, canonicalization, recipient identities, classification, edit planning, child ordering, and mapping decisions. Use the same production code and synthetic byte fixtures; inject clock/randomness only at the small test seams described in the implementation guide.
- Exercise real managed `System.IO`, `FileSystemWatcher`, and lock streams in isolated temporary directories on local NTFS. Use meaningful I/O failures, destination collisions, and process termination. Do not create a second filesystem implementation or require native Win32 test hooks.
- Run [scripts/Validate.ps1](scripts/Validate.ps1) from the repository root to restore locked dependencies, build [SmTagger.slnx](SmTagger.slnx) in Release with the pinned SDK, verify formatting, publish both production executables, and run the tests. The TRX report is written under `artifacts/test-results/`. [scripts/Publish-Release.ps1](scripts/Publish-Release.ps1) produces the [documented release artifacts](storage-reference.md#release-and-repository-trees). Use these production executables for black-box and deployment checks. Verify both distribution forms, including standalone EXEs copied into a directory with no companion DLLs.
- Production CLI, environment, configuration, and message data must provide no route to select fake storage, time, randomness, or faults. Run mail experiments only with controlled test accounts and destinations.

Three optional local compatibility tests read private captures from `samples/` without modifying the originals or copying them into repository fixtures or release artifacts. They report explicit discovery skips when the folder is absent and suppress private values in failure output. Published-executable tests also report explicit skips until both release executables exist; the complete validation script publishes before testing. Keep local fixture compatibility distinct from approval of a live server/client route.

The executable contracts are:

```text
sm-sorter.exe <datadir> [-l <logfile>] [-v] [-c] <spooldir> [<basename>]
sm-tagger.exe <datadir> [-l <logfile>] [-v] [-c] [-keep] <spooldir> [<basename>]
```

Capture before/after directory inventories and exact HDR/EML bytes, exit codes, standard error, each program's stdout with `-v` and/or `-c` and selected log with `-l`. Hash untouched bodies and pass-through pairs. Logs are supplementary evidence: their absence, corruption, or failed writes do not prove mail failed. Inspect retained file states and the independent receiver for publication/delivery outcomes.

No refolding; unchanged physical lines, removed fields, opaque headers, bodies, HDR files, and no-match pass-through remain outside this check. |
| UNIT-011: Sorter input readiness | Check final EML attributes before any HDR read/probe, including one-shot mode. Missing EML is stale in watch mode and deferred untouched in one-shot mode; directory/other attribute failures hold. With EML present, missing HDR is stale in watch mode and `MISSING_HDR` failure in one-shot mode. HDR read-only access with `FileShare.Read` excludes writers and its handle closes before claim. ## Best-effort logging cases

Logging is never a mail-success prerequisite. Test against both fresh and existing mappings and confirm the **same current message/child continues** after a logging-only failure; checking only a later message would miss this contract.

- `LOG-001`: Without `-l`, the tagger never touches a file trace or an old datadir `log.txt`, even when corrupt, absent, or inaccessible; the sorter accesses no email log. Without `-v`, neither emits debug stdout. Without `-c`, neither emits concise stdout; without either console flag, stdout is quiet. Per-mapping tag-log attempts remain independent of all three flags. The sorter has no implicit dependency on tagger logs, configuration, mappings, or EML contents.
- `LOG-002`: With tagger `-l <logfile>`, check explicit absolute/relative paths, existing-parent requirement, new event formatting, escaped controls, sequence/context, and honest intent/result state. Fail open/write/flush/dispose at meaningful points: report to stderr, disable only the file trace for that invocation, and continue the same mail operation and independent verbose output. A logging-only failure does not change its success exit code.
- `LOG-003`: Accept absent, unreadable, malformed, or incomplete diagnostic log contents without invalidating a sender-id record/mapping or blocking startup. Append new entries without reading, repairing, truncating, or adding recovery separators to existing bytes. A newly allocated mapping remains publishable when best-effort empty tag-log creation fails.
- `LOG-004`: For a child using individual and group tags, attempt each distinct tag-log append in ordinal tag-address order immediately before publication. Fail one append and verify standard error, remaining append attempts, and the same child's EML/HDR publication continue. Preserve any partial bytes. A later fresh message naturally attempts the affected tag log again.
- `LOG-005`: Fail parent diagnostic output and standard error as well as file logging. Preserve the underlying mail result and actual residual state; do not introduce recursive logging, a second fallback system, or an automatic repair attempt. A real mail/configuration failure still has its specified failure scope even if its diagnostic cannot be written.
- `LOG-006`: Sorter email-log records contain exactly one terminal `PASS`, `DIVERT`, or `ERROR` per completed processing attempt, with UTC timestamp, escaped basename/auth/reason, and actual known file locations. Cover no-auth, non-enrolled and enrolled routing, upstream `Failed`, unsafe completed HDR, unreadable enrollment, readiness-check failure, EML disappearance after ownership, partial handoff, explicit missing one-shot HDR when EML exists, and fatal HDR ownership failure. Successful and failed upstream-retention attempts each keep `UPSTREAM_FAILED`, actual current paths, and the attempted retention target; failed operations also report their I/O error without a second terminal record. Suppress records for HDR-only attempts, readiness deferrals in either mode, stale watcher entries, and all lifecycle/scan activity. Append UTF-8 without BOM plus CRLF, preserve corrupt/partial existing bytes, and never read or repair old log contents.
- `LOG-007`: Fail sorter email-log formatting/open/append/flush/close, including a missing parent directory. Report to stderr, disable only that file for the invocation, and preserve the current message's result, later mail processing, and exit status. Verify no parent creation, rotation, retry, or recursive fallback; a later invocation may open the log afresh. Independently fail verbose console output without affecting mail or the email log.
- `LOG-008`: With sorter `-v`, verify stdout lifecycle, scans, `DEFER` reasons/paths, routing, file operations, stale entries, and shutdown. Cover `HDR_WRITING` and `HDR_STATUS_UNEXPECTED`; neither creates a terminal email-log record. `Writing` is quiet on watch-mode stderr, while unexpected/incomplete status reports stderr on every encounter regardless of flags with no deduplication state. All one-shot deferrals report `NOT READY` and return 1. Check unchanged upstream `Failed` reporting. Test `-l` alone, `-v` alone, both, and neither in both modes, including the published executables. Confirm debugging adds no EML reads or tagger-only dependencies.
- `LOG-009`: Test tagger `-l` alone, `-v` alone, both, and neither in one-shot/watch modes and both release distribution forms, with `-keep` unchanged. Console events have `DEBUG ` prefix and match file event contents/run/sequence. Fail console writes and flushes while file logging continues; never close the caller-owned writer. Fail shared event formatting and run-ID initialization, disable all requested trace outputs best effort, and preserve successful mail. No trace output or configuration access occurs before both locks; check contention and invalid arguments leave selected files untouched. Ordinary errors remain on stderr regardless of flags.

- `LOG-010`: Verify both programs' `-c` in one-shot/watch modes and both release distribution forms, alone and in every combination with `-v`/`-l`, with no flag precedence or implicit file logging. Check usage hints, option order, duplicate `-c`, and missing `-l` values adjacent to `-c`. One completed sorter pair produces one summary with `PASS` for `spool`, `TAKE` for `process`, or `FAIL` for `failed`, replacing `from` after the basename and omitting the trailing destination clause; tagger pass-through produces one unchanged-parent summary; fan-out produces exactly one per published child. Check local `yyyy-MM-dd HH:mm:ss` timestamps, original positional HDR envelope sender, original recipients for unchanged pairs, individual recipient for each child, canonical auth/no-auth/unknown, null sender `<>`, and missing display fields `unknown`. Visible EML addresses and HDR `from:` metadata must not replace the positional envelope. Exercise malformed but passable positional values without new validation, tagger no-match recipient data, multiple recipients, raw controls, and Unicode line separators while maintaining one physical line. Confirm the sorter performs no EML reads or tagger-only configuration access for display.
- `LOG-011`: For concise tagger children, test newly created and reused individual mappings, later messages and restarts, and shared group mappings without adding a group-tag clause. Compare unchanged `-l` event sequences/records and per-mapping log behavior with concise enabled/disabled. Suppress concise mail summaries before full transfer, for deferral/stale paths, internal state renames, mapping allocation, pending construction, and first/second move failures. On later sibling or parent-cleanup failure, preserve only the lines already emitted for completely published children. Complete upstream `Failed` retention prints its one line while retaining stderr and nonzero one-shot result; partial retention prints no mail summary. Fail concise extraction/formatting/write/flush and stderr with narrow internal seams or real output failures: mail and available verbose/file output must continue, concise output disables itself after an output failure, and the caller-owned console writer remains open. No cross-message logging state, retries, or mail mutations may be introduced.

- `LOG-012`: With `-c`, verify both programs announce their name/version, watch or one-shot mode (including basename), and resolved absolute data/spool paths after required locks, before queue processing. Check tagger welcome precedes configuration load and `starting` does not claim readiness. After successful configuration and mapping load, verify one tagger summary with loaded sender-record count (not auth-index count) and all live individual/group mappings, including zero counts and excluding inert staging. Configuration/mapping failure may show the welcome but no load summary; invalid arguments and lock contention show neither. Use already loaded collections without extra reads/scans, sorter configuration access, or updated counts after new allocations. Check startup line timestamps/escaping, all output-flag combinations, and startup output failure disabling later concise summaries while mail and other sinks continue. Existing per-pair checks distinguish startup lines from mail summaries.

## Completion and reruns

Before marking a deployment supported, record applicable unit/integration/release results and complete each empirical assumption for the actual scope, or record an explicit disposition permitted by the specification. Record `ASSUMPTION-PRIVATE-PROVISIONING` during onboarding and preserve the accepted `ASSUMPTION-TEMPLATE-LENGTH` decision. Keep MDNs disabled until their separate evidence gate is met.

For later changes, use the stable assumption markers to select the affected laboratory cases and relevant C# regression tests. New failures or behavior changes return affected evidence to `PENDING`; passing tests for an older build do not approve a newer one. This plan does not implement automatic recovery, inbound lookup, MIME rewriting, native service integration, or monitoring from [future.md](future.md).
