# Mail workspace — rc.10 migration

Local candidate **1.0.0-rc.10** moves mail working state from the datadir into a fixed workspace beneath the selected SmarterMail Proc directory. The authoritative [runtime trees](storage-reference.md#runtime-directory-trees), [creation rules](storage-reference.md#required-directories-and-creation), and [lock locations](storage-reference.md#locks) define the current layout; this document describes only the offline conversion and rollback.

Configuration, permanent mappings, mapping staging, and `log.txt` stay in the datadir. The data volume may differ from the mail volume, provided each mapping/auth-index publication stays on its required data volume. All mail moves stay on the spool's ordinary local NTFS volume without junctions. The tagger acquires the existing data lock first, creates the fixed mailroot, then acquires its queue lock before trace/configuration/message work. Both locks remain held for the invocation, preventing conflicts through either datadir or spool.

The owner confirms SmarterMail does not read mail inside Proc. That version-sensitive isolation assumption is accepted for this relocation; it is not a newly measured live result. The sorter scans only direct Proc entries and does not enter the workspace. Failed retention remains inert and manual, with the same failed outcome and EML-first/suffixed-HDR-last move order. The change introduces no automatic fallback, queue migration, replay, or cleanup.

## Offline conversion

1. Pause upstream SmarterMail processing, affected submissions, and administrative changes. Stop both sorter and tagger and confirm their owning processes have exited. Record actual data/spool paths, launch identities/arguments, and both old binary hashes. Inspect paths only after all queue writers are quiescent; do not treat a stopped sorter alone as proof that SM stopped producing mail.
2. Take and verify a complete protected backup of the existing datadir and any existing mail workspace, with file inventories, byte hashes, and required permissions. Record and preserve the remaining direct Proc and normal-spool states as part of the same stopped checkpoint. Include configuration, mappings, both staging trees, every message suffix and diagnostic, debug copies, logs, and prior binaries. A datadir-only checkpoint is insufficient after rc.10.
3. For installations predating rc.9, complete the [sender configuration conversion](sender-configuration-2026-09-17.md), including the [earlier path conversion](sender-layout-2026-09-17.md) if needed, without starting either intermediate version. Record deliberate changes separately from the queue relocation. Previously retired indexes must not accidentally become active.
4. Resolve the old datadir queue paths and the new fixed mailroot defined by the storage reference. Verify the exact source and destination paths are within their intended roots, are ordinary local NTFS directories without junctions, and that each queue move is within the spool volume. The earlier supported layout placed these queues on that volume already. If changing volumes as well, stop and plan a separately verified offline transfer; do not rely on a cross-volume rename or runtime copy/delete fallback. Configuration may be placed on another data volume independently, with a verified complete data copy and coordinated launch paths.
5. Inventory `<datadir>\process` and `<datadir>\failed` as historical sources. Record legitimately absent directories as absent; do not invent old queues. Require each corresponding new destination to be absent. If old and new directories both exist, or any destination contains state, stop and reconcile their full inventories offline; do not merge, overwrite, or delete one to make the move succeed.
6. Create only the fixed mailroot parent as needed, then move each existing historical queue directory as a whole to its corresponding `process` or `failed` destination using a same-volume, non-replacing directory move. Preserve all files, names, suffixes, bytes, diagnostics, debug copies, and subentries exactly; this move must not activate, rename, or replay any retained state. Stop after the first failed move, record the exact partial layout, and leave both programs stopped. Never roll completed moves back automatically or overwrite an existing destination.
7. Leave sender configuration, mapping staging, permanent tag records, their identity files/logs, and the datadir trace at their data locations. Keep the datadir lock file; it is not moved into the mailroot. The new queue lock is a separate runtime-created ownership file, not a replacement for the data lock. Old lock filenames alone are not evidence of an active process.
8. Compare complete source/backup and destination inventories and hashes, accounting for only the approved directory relocation and any separately recorded configuration conversion. Verify no old queue directory remains for a completed move and no message file disappeared, changed suffix, or changed bytes. Check permissions on both roots. Retain the protected backup and partial-state records; do not dispose of evidence or original mail as part of conversion.
9. Deploy both matching rc.10 binaries together and update every scheduled, wrapper, and manual launch path. The CLI still takes datadir and spooldir; there is no independently selectable workspace argument. Do not start an older binary against the new queues or a new binary while old queues remain awaiting conversion. The program will neither detect nor drain those old queues for you.
10. Save a post-conversion checkpoint before starting workers. Startup may immediately process plain queued input; it is not a read-only validation. Resume the approved flow only after every queued/retained item's location and disposition is accounted for. Check fresh controlled sorter pass-through, enrollment diversion, and tagger output against the new paths, with unchanged mappings and bytes. The wider deployment gates remain as recorded in [assumptions.md](assumptions.md); this relocation relies on the accepted Proc-subtree isolation assumption and does not require a new live trial to reopen that decision.

## Rollback and continuing backups

Before any new post-cutover state exists, stop both workers and upstream processing and restore the complete coordinated prior checkpoint, prior queue locations, both prior binaries, and launch paths. Never overlay a backup onto a partially migrated live tree or leave two apparent live copies of a queue. Preserve uncertain states separately for manual reconciliation; no executable performs rollback.

If any post-cutover mail, mapping, log, or configuration state exists, first reconcile it offline against the backup and external delivery evidence. Preserve new mappings permanently and account for any output that may already have been delivered. Restoring only the old datadir or copying old plain pairs back into a queue can lose tag history or duplicate mail. Do not resume until every changed state has an explicit disposition.

Future backups must coordinate the complete datadir, complete mailroot, and separately preserved direct Proc/spool state while writers are stopped. This remains necessary when the data and mail volumes differ. Neither program creates backups or supplies a cross-volume transaction.

## Verification scope

This document specifies an offline operator procedure; preparing it does not migrate actual server data or change SmarterMail settings. Record current build, automated-test, artifact, and any isolated migration results in [validation-report.md](validation-report.md). Earlier live retention and tagging reports used their documented datadir queues and do not prove a fresh live run of the rc.10 layout. The accepted owner-confirmed SM isolation assumption and remaining deployment gates are tracked separately in [assumptions.md](assumptions.md).
